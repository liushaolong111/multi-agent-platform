一、背景与目标

1.1 背景

工程企业在项目管理过程中，成本、质量安全、制度规范等数据分散在业务系统和文档中，管理人员获取信息需要跨系统查询、人工汇总，效率低且口径不统一。

1.2 目标

  • 可观测结果：用户输入自然语言问题后，系统在合理时间内返回包含精确数字和数据来源的回答
  • 数据准确：回答中的数字来自程序计算（pandas 预计算）或真实数据库查询（Text-to-SQL），不依赖文档中的模糊数字
  • 权限隔离：不同角色用户只能看到其权限范围内的数据

1.3 分层架构

系统按职责分为七层，自上而下依次为交互层、智能体编排层、工具层、技能层、并发与缓存层、数据层、外部集成层，各层之间单向依赖，下层为上层提供能力。

三、用户画像与角色权限

3.1 用户画像

集团管理员 admin

关注：全公司成本、安全、质量的整体态势，需要全局视图和横向对比。

典型问题：

"2026年上半年各区域的项目成本排名和预算执行率？"
"哪些项目的安全问题闭环率低于80%？"
"华东区和华北区的成本结构有什么差异？"

区域经理 manager

关注：本区域内的项目成本、安全、质量状况，需要及时发现和处理问题。

典型问题：

"我们华东区这个月的成本超支了多少？"
"华东区有哪些未闭环的重大安全隐患？"
"BY-HD-001项目的预算执行率是多少？"

只读用户 viewer

关注：查询制度规范、了解项目基本情况，仅有查看权限。

典型问题：

"成本超支5%以上需要走什么审批流程？"
"高处作业的安全规范有哪些要求？"
"质量安全问题的整改闭环标准是什么？"

3.2 角色权限矩阵

角色数据范围功能权限文档可见性
集团管理员 admin全部区域、全部项目查询、审批全部（含 company 级敏感文档）
区域经理 manager仅所属区域查询、审批仅 public 级
只读用户 viewer按配置的可见范围仅查询仅 public 级

3.3 权限规则

  • 行级隔离：区域经理的所有数据出口（SQL 查询、RAG 检索、统计结果、图表生成）均自动追加区域过滤条件，无法通过任何路径获取其他区域数据
  • 文档可见性：包含敏感经营数据的文档标记为 company 可见性，仅管理员可检索；普通制度文档为 public，全员可见
  • 身份来源：所有请求以 JWT 令牌中的身份为准，请求体中的 user_id 不可覆盖令牌身份

六、核心用户流程

6.1 提问与回答主流程

用户登录 ↓ 输入自然语言问题 ↓ [意图分类] → data_analysis / report_generation / knowledge_query ↓ [任务拆解] → 拆分为 2-4 个子任务 ↓ [并行执行子任务] ├─ pandas 预计算精确统计（Redis 缓存 300s + asyncio.to_thread 并发） ├─ 多路召回知识库片段 └─ LLM 组织语言 ↓ [多智能体专家协作] ├─ 成本专家（预算执行率/超支预警视角） ├─ 安全专家（隐患/闭环率/预警视角） └─ 材料专家（库存/到货滞后/预警视角） → 三专家 asyncio.gather 并行 ↓ [协调者] → 聚合三专家意见，指出跨域关联 ↓ [ReAct 工具循环] ├─ 判断是否需要调工具 ├─ 调 Text-to-SQL 查业务库（按需） └─ 观测回喂 → 再决策（最多 N 轮） ↓ [结果审核] → 校验数字完整性 ↓ 返回回答（流式推送）

6.2 权限校验流程

用户请求携带 JWT ↓ 解析令牌 → 确定角色与区域 ↓ 数据出口校验 ├─ SQL 层：自动追加 region 过滤 ├─ RAG 层：按 visibility 过滤文档 └─ 统计层：按区域过滤数据 ↓ 返回权限范围内的结果

七、功能需求

FR-01 用户认证

P0

触发：用户访问平台时

处理规则：用户通过用户名密码登录，服务端验证后签发 JWT 令牌；后续所有请求必须携带令牌，无令牌或令牌无效则拒绝访问；令牌中包含用户角色和区域信息。

结果：登录成功后进入问答界面

验收标准：未携带令牌的请求返回 401；令牌解析出的角色与区域与数据库一致；请求体中的 user_id 不影响令牌身份。

FR-02 自然语言问答

P0

触发：用户在输入框提交问题

处理规则：

  • 系统接收用户问题，创建或复用会话
  • 问题经意图分类、任务拆解后执行
  • 回答通过 SSE 流式推送给前端
  • 回答中引用的数据需标明来源

结果：返回带精确数字和来源标注的回答

异常：模型不可用时返回降级提示，不阻塞

验收标准：回答中至少包含一个来自程序计算或数据库查询的精确数字；回答中标注数据来源（预计算/SQL/文档）。

FR-03 意图识别与任务拆解

P0

触发：收到用户问题后

处理规则：

  • 意图分类：将问题分为 data_analysis、report_generation、knowledge_query 三类
  • 任务拆解：复杂问题拆分为多个可并行执行的子任务
  • 分类结果不合法时回退为 knowledge_query

验收标准：分类结果在三类枚举内；子任务数量 1-4 个。

FR-04 知识检索（多路召回）

P0

触发：子任务执行时需要知识库内容

处理规则：

  1. 分桶路由：根据查询推断业务域（成本/安全/质量/技术/管理/材料/天气），优先在目标域内检索，不足时回退全量
  2. 双路召回：向量语义检索（FAISS）+ 关键词检索（BM25）并行执行
  3. RRF 融合：用倒数排名融合两路结果，解决分数尺度不一致问题
  4. MMR 精排：平衡相关性与多样性，避免召回结果高度重复
  5. RBAC 过滤：按用户权限过滤文档可见性

结果：返回 top-k 相关文档片段

异常：向量库不可达时返回空结果，不阻塞主流程

验收标准：召回文档的 business_domain 与查询推断的域匹配率≥80%；manager 角色无法召回 visibility=company 的文档。

FR-05 数据查询（预计算 + Text-to-SQL）

P0

触发：子任务需要精确数字时

处理规则：

  • pandas 预计算：固定维度统计（总成本、预算执行率、分区域/类别/项目/月度；安全闭环率与严重程度分布；材料类别分布与到货滞后）由程序直接计算
  • 三级预警分级：成本（执行率≥105%黄/≥110%橙/≥115%红）、安全（重大未闭环红/较大未闭环橙/一般超30天未闭环黄）、材料（滞后天数1-5黄/5-10橙/>10红），由程序判定后注入回答
  • 结果缓存：统计结果写入 Redis 缓存（TTL 300s），相同区域的重复请求直接命中缓存，避免每次重读 CSV；Redis 不可达时降级为进程内内存缓存
  • 异步并发：成本/安全/材料三域统计用 asyncio.to_thread 放到线程池并通过 asyncio.gather 并发执行，避免阻塞事件循环
  • Text-to-SQL：预计算覆盖不了的灵活查询，由 LLM 生成 SELECT 语句查业务库
  • 只读防护：仅允许 SELECT，禁止写操作；无 LIMIT 自动追加；结果截断 100 行
  • 自愈重试：SQL 执行报错时，把错误回喂 LLM 修正一次

权限：区域经理的 SQL 自动追加 region = '所属区域' 过滤

验收标准：SQL 仅包含 SELECT/WITH；无 LIMIT 时自动追加；区域经理的 SQL 必含 region 过滤条件。

FR-06 工具调用循环（ReAct）

P0

触发：初步回答生成后，判断是否需要补充查询

处理规则：

  • LLM 决定调用哪个工具（Function Calling），支持一次决策多个工具
  • 工具执行结果回喂，LLM 再决策，形成"思考-行动-观察"循环
  • 循环终止条件：LLM 决定不再调工具 或 达到最大轮数

验收标准：循环轮数不超过 MAX_TOOL_ROUNDS；工具调用参数与工具定义匹配。

FR-07 人工审批闸门

P1

触发：开启审批模式时，工具调用前

处理规则：

  • 高危操作（如大范围数据查询）需展示给用户确认
  • 用户批准后执行，拒绝则跳过

验收标准：审批模式开启时，工具调用必须经过用户确认；审批状态持久化，会话恢复后可继续。

FR-08 结果审核

P0

触发：回答生成后

处理规则：

  • 检查回答是否包含具体数字（避免空泛回答）
  • 审核通过的问答写入长期记忆
  • 审核不通过则不存储

验收标准：不含数字的回答被标记为未通过；未通过的回答不出现在长期记忆检索结果中。

FR-09 短期记忆

P1

触发：同一会话内的多轮对话

处理规则：保存上一轮回答的摘要，注入下一轮 prompt；会话超时后自动清理。

降级：Redis 不可用时使用进程内内存存储

验收标准：同一会话内第二轮提问能引用第一轮回答的内容。

FR-10 长期记忆

P1

触发：回答审核通过后

处理规则：存储用户的历史问答对，跨会话留存；新会话提问时，检索最近 N 条历史问答作为上下文。

降级：数据库不可用时静默跳过，不阻塞

验收标准：新会话中检索到上一会话通过审核的问答。

FR-11 多智能体专家协作

P1

触发：Skill 节点产出初步分析后

处理规则：

  • 三领域专家：成本专家（预算执行率/超支预警视角）、安全专家（隐患/闭环率/预警视角）、材料专家（库存/到货滞后/预警视角），各有独立角色 prompt，只看自己领域的统计数据
  • 并行执行：三专家通过 asyncio.gather 并行调用 LLM，延迟 ≈ 单次调用
  • 协调者聚合：协调者节点聚合三专家的专业分析，融合成连贯的综合回答（保留关键数字和预警等级，指出跨域关联，如"成本超支可能与材料滞后有关"）
  • 降级：专家分析全空时直接透传 Skill 结果，不阻塞主流程

设计取舍：不采用全自主群聊（CrewAI/AutoGen 式），避免不可控和延迟过高；采用"一轮并行分析 + 聚合"模式，兼顾专业深度和响应速度。

验收标准：回答中包含至少两个领域的专业视角；协调者指出跨域关联；三专家延迟不超过单次 LLM 调用的 1.2 倍。

FR-12 缓存与分布式锁

P1

触发：统计计算、灌库、用户创建、长期记忆写入等场景

处理规则：

  • Redis 缓存：pandas 统计结果用 @cached 装饰器缓存，TTL 300s，key 带参数 hash；Redis 不可达时降级为进程内内存缓存
  • 分布式锁：灌库、用户创建、长期记忆写入等临界区使用 Redis 分布式锁（SETNX + 唯一 token + 看门狗自动续期），释放时用 Lua 脚本原子校验 token 防止误删；Redis 不可达时降级为进程内 threading.Lock

降级：Redis 不可达时，缓存降级为进程内内存，锁降级为进程内互斥锁，功能不中断。

验收标准：相同区域的重复统计请求命中缓存不重复计算；并发灌库时只有一个进程执行；锁释放时不误删他人持有的锁。

八、共享规则与异常处理

8.1 数据准确性原则

  • 数字交给程序：所有统计数字由 pandas 预计算或 SQL 查询生成，LLM 仅负责组织语言
  • 结构化数据不进向量库：业务明细数据不向量化，避免绕过 SQL 层的权限隔离
  • 文档数字不作事实依据：RAG 检索的文档仅用于背景和口径说明，不作为数字来源

8.2 优雅降级规则

依赖不可达时行为
LLM 服务返回降级提示文本，不阻塞请求
Redis（短期记忆/缓存/分布式锁）短期记忆降级为进程内内存；统计缓存降级为进程内缓存；分布式锁降级为进程内 threading.Lock
数据库（长期记忆）跳过长期记忆读写
向量库跳过知识检索，仅用预计算统计
业务数据库Text-to-SQL 不可用，返回提示

8.3 安全规则

  • SQL 三层防护：静态关键字校验 + 强制 LIMIT + 异常兜底

9.1 多路召回流程

def multi_route_search(query, k=3, user): # 1. 分桶路由 domain = infer_domain(query) # cost / safety / quality / ... candidates = search_in_domain(domain, k*3) if len(candidates) < k: candidates += search_all(k*3) # 回退全量 # 2. 双路召回 dense = vector_search(query, candidates, k=k*3) sparse = bm25_search(query, candidates, k=k*3) # 3. RRF 融合（粗排） fused = rrf_fuse(dense, sparse, k=RERANK_CANDIDATES) # 4. MMR 精排 reranked = mmr_rerank(query, fused, k=k, lambda=0.7) # 5. RBAC 过滤 return filter_by_visibility(reranked, user)

9.2 ReAct 决策-执行循环

def react_loop(state, max_rounds=5): for round in range(max_rounds): # Thought + Action：LLM 决定调不调工具、调哪个 tool_calls = llm.decide_tools(state) if not tool_calls: break # 收敛：模型决定不再调工具 # Act + Observation：执行工具，累积观测 for call in tool_calls: result = execute_tool(call) state.observations.append(result) return state # 超过 max_rounds 强制熔断

9.3 RBAC 区域隔离（Text-to-SQL 层）

def generate_sql(question, user): prompt = schema + question if user.role == "manager": # 注入区域约束，LLM 生成的 SQL 必须带 region 过滤 prompt = f"你只能查询{user.region}区域的数据。\n" + prompt sql = llm.generate(prompt) # 第二道防线：静态校验 SQL 是否带区域过滤 if user.role == "manager" and not has_region_filter(sql, user.region): raise PermissionError("SQL 未限定区域") return sql

9.4 多智能体专家协作

async def experts_node(state): # 三专家并行：各自只用本领域统计 + 独立角色 prompt cost_analysis, safety_analysis, material_analysis = await asyncio.gather( llm.ainvoke(COST_EXPERT_PROMPT + state.cost_stats), llm.ainvoke(SAFETY_EXPERT_PROMPT + state.safety_stats), llm.ainvoke(MATERIAL_EXPERT_PROMPT + state.material_stats), ) # 降级：全空则透传 Skill 结果 if not any([cost_analysis, safety_analysis, material_analysis]): return {"tool_result": state.tool_result} return {"expert_analyses": [cost_analysis, safety_analysis, material_analysis]} async def coordinator_node(state): # 聚合三专家意见，指出跨域关联，写回 tool_result analyses = state.expert_analyses final = await llm.ainvoke(COORDINATOR_PROMPT + analyses) return {"tool_result": final}

class RedisLock: def acquire(self): token = uuid4() # SET key token NX EX ttl：原子获取锁 ok = redis.set(name, token, nx=True, ex=ttl) if ok: self.start_renew_daemon() # 看门狗自动续期 return True return False def release(self): # Lua 脚本原子校验 token + 删除，防止误删他人锁 lua = """ if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) end """ redis.eval(lua, 1, name, token)
